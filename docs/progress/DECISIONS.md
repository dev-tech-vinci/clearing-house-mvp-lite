# Decisions Log

> Architectural or scope decisions made while executing the build plan, with rationale. The build plan (`docs/CLAUDE_CODE_BUILD_PLAN.md`) already records the major upfront decisions (package structure, API design, processing pattern) — this log is for decisions made *during* implementation that aren't already captured there.

## Phase 1

- **`/support` and `/admin` reuse the plain `/home` auth gate, not a role gate.** The build plan's Phase 1 scope is route skeletons only — organizations, memberships, and roles don't exist until Phase 2. Rather than leave the new portals unprotected (or invent a role check against tables that don't exist yet), `middleware.ts` extracts the existing `/home` logic into `requireAuthHandler` and applies it to all three route groups identically: any authenticated user (who has passed MFA) can currently reach `/support` and `/admin`. This is called out in code comments on both matcher entries and must be replaced in Phase 2 with `has_org_access`/`has_permission` checks — do not treat current `/admin` or `/support` access as a real permission boundary.
- **`docs/01-repository-baseline.md` was missing at the start of this work session** even though Phase 0's acceptance criteria required it and `CLAUDE.md`/the build plan reference it. It was created retroactively from the "Verified repository baseline" section already recorded in `docs/CLAUDE_CODE_BUILD_PLAN.md` (section 0) plus toolchain versions re-verified live (`node -v`, `pnpm -v`, `git rev-parse HEAD`), rather than re-running a from-scratch `pnpm install`/`supabase:start` against a clean baseline checkout (Phase 1 changes were already present in the working tree, so a "pure baseline" command run was no longer obtainable). The doc says so explicitly rather than presenting reconstructed data as a fresh baseline run.
