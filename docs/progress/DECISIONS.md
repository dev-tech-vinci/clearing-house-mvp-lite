# Decisions Log

> Architectural or scope decisions made while executing the build plan, with rationale. The build plan (`docs/CLAUDE_CODE_BUILD_PLAN.md`) already records the major upfront decisions (package structure, API design, processing pattern) — this log is for decisions made *during* implementation that aren't already captured there.

## Phase 1

- **`/support` and `/admin` reuse the plain `/home` auth gate, not a role gate.** The build plan's Phase 1 scope is route skeletons only — organizations, memberships, and roles don't exist until Phase 2. Rather than leave the new portals unprotected (or invent a role check against tables that don't exist yet), `middleware.ts` extracts the existing `/home` logic into `requireAuthHandler` and applies it to all three route groups identically: any authenticated user (who has passed MFA) can currently reach `/support` and `/admin`. This is called out in code comments on both matcher entries and must be replaced in Phase 2 with `has_org_access`/`has_permission` checks — do not treat current `/admin` or `/support` access as a real permission boundary.
- **`docs/01-repository-baseline.md` was missing at the start of this work session** even though Phase 0's acceptance criteria required it and `CLAUDE.md`/the build plan reference it. It was created retroactively from the "Verified repository baseline" section already recorded in `docs/CLAUDE_CODE_BUILD_PLAN.md` (section 0) plus toolchain versions re-verified live (`node -v`, `pnpm -v`, `git rev-parse HEAD`), rather than re-running a from-scratch `pnpm install`/`supabase:start` against a clean baseline checkout (Phase 1 changes were already present in the working tree, so a "pure baseline" command run was no longer obtainable). The doc says so explicitly rather than presenting reconstructed data as a fresh baseline run.

## Phase 2

- **Platform/support roles are seeded but get no cross-org RLS bypass in this phase.** `platform_super_admin`, `support_manager`, and `support_agent` exist in `roles` with their full permission-matrix rows in `role_permissions` (so the catalog is complete and documentation-accurate), but no policy or helper function grants them visibility into an organization they don't hold a membership row in. **Why:** the architecture explicitly ties platform/support cross-org access to the audited support-access-session model (assigned ticket, typed reason, time limit, full audit trail — "no silent impersonation"), which is Phase 8 scope. Shipping a cross-tenant bypass now, before that audit infrastructure exists, would be exactly the kind of unaudited backdoor the architecture prohibits. **How to apply:** tenant isolation is strict for every role through at least Phase 7; do not add a "platform admin sees everything" shortcut to any RLS policy before Phase 8 builds `support_access_sessions`.
- **Cross-member visibility (the "who else is in my org" members list) is not done by widening `accounts` RLS.** The obvious approach — make `user_profiles` a view that bypasses `accounts_read` — would let any authenticated user look up any other user's name/email platform-wide, which is worse tenant hygiene than the feature needs. Instead `user_profiles` stays exactly as restrictive as `accounts_read` (`security_invoker = true`), and a separate `SECURITY DEFINER` function, `get_organization_members(org_id)`, does the one legitimate cross-user read: it checks `has_org_access(org_id)` first, then reads `accounts` as its own owner (bypassing RLS internally, same pattern as the other helper functions) and returns only that org's members. **How to apply:** if a future phase needs another "see other users in my org" capability, prefer adding a narrow, permission-checked function over widening a base RLS policy.
- **`create_organization` and `accept_invitation` are RPCs, not direct table inserts, because of a bootstrap problem.** A brand-new org has no members yet, so no RLS policy keyed on `has_permission(org_id, ...)` can ever be satisfied for the very first insert into `organization_memberships`. Likewise, a freshly-invited user has no membership yet, so they can't satisfy an RLS check to insert their own membership row when accepting. Both RPCs are `SECURITY DEFINER` and perform exactly one bootstrap insert each; every other table operation in this phase goes through ordinary RLS-checked `INSERT`/`UPDATE` as the calling user's own client.
- **Bug found during this phase's own Playwright verification: a `'use server'` file cannot export a non-function value.** `server-actions.ts` originally also exported `CURRENT_ORGANIZATION_COOKIE` (a plain string constant) alongside the server actions. Next.js's `'use server'` directive requires every export from that file to be an async function; the constant export made the whole module fail to compile, which silently 500'd every `/home` page (visible only in the dev server's terminal log, not as a typecheck/lint failure — `tsc`/`eslint` don't know about this Next.js-specific constraint). Fixed by moving the constant to a plain `constants.ts`. **How to apply:** never add a non-function export to a `'use server'` file, even a "harmless" shared constant; give it its own module.
- **Bug found during the same verification: `get_organization_members()`'s declared `RETURNS TABLE` types didn't match the source columns.** `accounts.name`/`email`/`picture_url` and `roles.key`/`name` are all `varchar(n)`, but the function declared those output columns as `text`. Postgres treats `varchar(n)` and `text` as distinct types for `RETURNS TABLE` matching (unlike ordinary query contexts, where they're usually interchangeable), so every call failed with `42804 structure of query does not match function result type` — caught only by driving the members page in a real browser, not by `supabase db test` (the pgTAP suite calls the same function but happened to not trip the mismatch in a way that surfaces here) or by `tsc`. Fixed with explicit `::text` casts in the `SELECT`. **How to apply:** any future `RETURNS TABLE` function that reads `varchar` columns needs explicit casts to whatever type it declares.
- **Bug found during the same verification: closing a Radix `Dialog` opened from inside a `DropdownMenu` item, combined with a same-tick `router.refresh()`, could leave the dialog's full-screen overlay stuck intercepting all clicks.** This reproduced reliably (not a one-off flake) whenever the organization switcher's dropdown was reopened immediately after creating an organization. Root cause was two compounding issues: (1) the dropdown item's `onSelect` called `e.preventDefault()` to keep the dropdown "open" underneath the dialog, which left Radix's dropdown/dialog focus-trap handoff in an inconsistent state; (2) `router.refresh()` was called synchronously in the same callback that closed the dialog, landing in the same React commit as the close animation and interrupting it. Fixed by removing the item-level `preventDefault` (letting the dropdown close normally), adding `onCloseAutoFocus` on the dropdown content to stop it stealing focus back while the dialog is opening, and deferring every `router.refresh()` that follows a dialog/dropdown close to the next tick (`setTimeout(..., 0)`). **How to apply:** any new component that opens a Dialog from inside a DropdownMenu/Popover item should follow this same pattern (no item-level preventDefault, `onCloseAutoFocus` guard, deferred refresh) rather than rediscovering it.
- **`devIndicators: false` added to `next.config.mjs` as a side effect of chasing the bug above.** While debugging the stuck-overlay issue, the first (wrong) hypothesis was the pre-existing "Open Next.js Dev Tools" floating button documented in Phase 1's `KNOWN_ISSUES.md`. Disabling it via `devIndicators: false` turned out not to be the fix for the Radix issue, but it's a real, low-risk improvement in its own right: of the 3 Playwright specs that were failing before this phase (all due to that floating button intercepting clicks), 1 now passes outright. The other 2 (`account.spec.ts` "user can update their password", `password-reset.spec.ts`) now fail with a *different* symptom (`waitForURL('/update-password')` timing out) — a distinct, still-open issue, not the dev-tools button, and not something touched by this phase's code. Left open and re-documented in `KNOWN_ISSUES.md` rather than investigated further, since it's in account/password-reset flows outside Phase 2's scope.

## Phase 3

- **`payer_id` on `coverages` and `organization_payer_enrollments` is a nullable column with no foreign key yet.** `public.payers` doesn't exist until Phase 4. Both tables carry a required `payer_label` text field (e.g. `"SIM-MEDICARE-FFS"`) for display and identification until then. **How to apply:** Phase 4 must add `alter table ... add constraint ... foreign key (payer_id) references public.payers(id)` to both tables once the payer directory exists, and the UI's free-text payer-label inputs should be replaced with a real payer picker at that point — don't treat the current free-text field as permanent.
- **The build plan's "seed a few synthetic providers/patients" is satisfied by pgTAP fixtures and organic UI creation, not a permanent `seed.sql` row.** There is no stable demo organization to attach seed rows to — organizations are created dynamically per user via `create_organization`, and Phase 2 deliberately left `seed.sql` empty for the same reason. `apps/web/supabase/tests/database/entities-rls.test.sql` creates and rolls back its own synthetic provider/facility/patient/subscriber/coverage/enrollment fixtures per run, and any user can create their own via `/home/providers` and `/home/patients`. Phase 10 explicitly owns "demo seed" as its own deliverable once a stable demo org/seed flow is in scope — permanent seed rows are deferred there, not skipped.
- **Cross-org FK-consistency is enforced by `BEFORE INSERT/UPDATE` triggers on `subscribers` and `coverages`, not by RLS alone.** RLS stops a caller from *reading* another org's row, but nothing stops them from *creating* a row in their own org whose foreign key points at someone else's patient (e.g. a `subscribers` row with `organization_id = <mine>` but `patient_id` belonging to a different org). `kit.check_subscriber_patient_org()` and `kit.check_coverage_org_consistency()` (both `SECURITY DEFINER`, `set search_path = ''`) close that gap by verifying every relevant FK's `organization_id` matches the row's own `organization_id` before the write is allowed, and (for coverages) that `patient_id` matches the chosen `subscriber_id`'s own patient. Confirmed by the pgTAP suite's cross-org and same-org-mismatch negative tests. **How to apply:** any future table with an org-scoped FK into another org-scoped table needs the same trigger pattern — RLS alone is not sufficient.
- **All six new tables use `has_org_access` alone for CRUD, not a finer `has_permission` key, matching your explicit "org-owned CRUD is the acceptance gate" instruction.** The architecture's role-permission matrix doesn't define a specific permission for managing providers/facilities/patients/coverages, so gating writes on (for example) `claims.create_edit` would be inventing a mapping not in the matrix. Any authenticated member of an org can create/read/update these entities; deactivation is a reversible `is_active` toggle, not a hard delete. **How to apply:** if a later phase wants finer-grained gating here (e.g. restrict entity management to `claims_specialist`+), that's a new, explicit decision to make then — don't assume it retroactively.
- **Bug found during this phase's own Playwright verification: `providers.organizationName`/`firstName`/`lastName` combined `.min(1)` with `.optional()`, but the dialog's `defaultValues` initializes the currently-hidden half of the individual/organization split to `''` (empty string), not `undefined`.** `.optional()` only permits `undefined`; an empty string still has to satisfy `.min(1)`, which it fails. This blocked `ProviderDialog`'s submission entirely and silently: `form.handleSubmit` simply never calls `onSubmit` when client-side Zod validation fails, so there's no thrown error, no toast, and no network call — the dialog just stays open with no visible feedback. Confirmed by the complete absence of any `providers` insert attempt in the dev server log even after a successful-looking form fill and submit click. Fixed by dropping `.min(1)` from all three fields (non-emptiness where it actually matters — organization providers need a name, individual providers need first+last — is already enforced by the cross-field `hasRequiredNameForType` refine, which does a truthy check, plus the DB check constraint `providers_name_by_type`). **How to apply:** never pair `.min(1)` with `.optional()` on a field whose dialog `defaultValues` uses `''` rather than `undefined` for "not applicable right now" — this is a general pattern risk for any future entity dialog with a conditionally-hidden field, not unique to providers.

## Phase 4

- **Payers and payer rules are global reference data, not tenant-owned — a new `is_platform_admin()` helper, deliberately narrow in scope.** Every table since Phase 2 is scoped by `organization_id` + `has_org_access`/`has_permission`. A payer directory doesn't fit that shape: there is exactly one simulated "SIM Medicare FFS National" that every org needs to see identically, not one copy per tenant. `public.is_platform_admin()` (`SECURITY DEFINER`, `set search_path = ''`, mirrors the Phase 2 helper pattern) is true if the caller holds `platform_super_admin` in *any* organization membership, and is consulted only by RLS policies on the seven tables in `20260719015820_payers.sql`. **Why it's deliberately narrow:** Phase 2 explicitly decided platform/support roles get no cross-org bypass into tenant-owned data until Phase 8's audited support-access-session model exists (see Phase 2 decisions above) — `is_platform_admin()` must not become a backdoor into organizations/patients/providers/claims. **How to apply:** any future global (non-tenant-owned) reference table should reuse `is_platform_admin()` the same way; never extend it, or a lookalike, to gate access to a tenant-owned table.
- **`payer_rules.payer_id` is nullable, with the required-vs-null rule enforced by both a DB `CHECK` and a Zod refine, not the DB alone.** `universal`/`claim_type`/`informational` rules apply across all payers (`payer_id` null); `payer_edit`/`adjudication` rules are payer-specific (`payer_id` required). The DB constraint `payer_rules_payer_scope` is the real boundary; the client-side Zod refine (`payerRequiredForScope`) exists only so the dialog can show a field-level error before a wasted round trip, matching the "DB is the real gate, Zod is UX" pattern already used for the `providers_name_by_type` constraint in Phase 3.
- **Bug found during this phase's own Playwright verification: `payer-rule.schema.ts`'s `payerId` field repeated the exact Phase 3 bug class.** `payerId: z.string().uuid().optional()` rejected `CreateRuleDialog`'s `''` default for the payer field, which is hidden for `universal`/`claim_type`/`informational` categories. Same silent-failure signature as Phase 3's provider-name bug: no thrown error, no toast, zero `payer_rules` POST attempts in the dev log despite a successful-looking submit. Fixed the same way Phase 3 documented as the general pattern: `z.union([z.literal(''), z.string().uuid()]).optional()`. **How to apply:** this is now a two-occurrence pattern (Phase 3 provider names, Phase 4 payer rule) — any new dialog with a conditionally-hidden field whose Zod type isn't `z.string()` needs the same `z.union([z.literal(''), <real type>])` treatment, not `.optional()` alone.
- **pgTAP's `throws_ok` cannot assert an RLS `UPDATE` denial.** Postgres treats a failing `USING` clause on `UPDATE` as a row filter — the statement succeeds and reports 0 rows affected, it does not raise — unlike `INSERT`'s `WITH CHECK`, which does throw `new row violates row-level security policy`. The original `payers-rls.test.sql` assertion used `throws_ok` for the non-admin-update-denied case and would have silently never caught a real RLS regression (a broken policy that let the update through would still not throw). Fixed by asserting the target row's value is unchanged after the attempted update. **How to apply:** any future pgTAP negative test for `UPDATE`-via-RLS must assert "value unchanged," never `throws_ok`; `throws_ok` stays correct for `INSERT`/`DELETE` RLS denials.
- **The CSV import 409/500 bug: the real defect was a schema re-validation mismatch, not a PostgREST conflict.** `PayerCsvImportDialog` parses raw CSV text client-side through `PayerImportRowSchema`, whose `enrollment_required`/`is_active` fields are declared as `z.string()...transform(...)` — the *input* is a CSV string (`"true"`/`"false"`), the *output* (what ends up in component state) is a real boolean. That already-transformed row was then sent as-is to `importPayersAction`, whose `enhanceAction` wrapper re-validates every argument against `ImportPayersSchema`, which (before the fix) reused the exact same `PayerImportRowSchema` — so the server-side re-validation expected raw CSV strings again and rejected the real booleans it had itself produced one hop earlier, with `Expected string, received boolean`. This was hard to diagnose because the *first* symptom observed was a `409 Conflict` from the Supabase upsert call, which sent debugging down an unrelated path (PostgREST `Prefer: count=exact` upsert semantics, reproduced and ruled out via direct psql and service-role HTTP calls — none of which touched the actual client→server-action validation boundary where the real bug lived). Removing `count: 'exact'` did not fix anything; only inspecting the dev server's `ZodError` log output (not visible in any of the manual SQL/curl reproductions) surfaced the real cause. **Fix:** added `ParsedPayerImportRowSchema` — same shape, but `enrollment_required`/`is_active` are plain `z.boolean()` — and pointed `ImportPayersSchema` (used by both `importPayersAction` and `POST /api/v1/payers/import`) at it instead of re-using the CSV-parsing schema. **How to apply:** a schema that performs a `.transform()` on the client is validating the *input* shape; never reuse that same schema to re-validate the *output* on the far side of a client→server boundary — the input and output types are different on purpose, and re-validating with the wrong one fails in a way whose error message (a `409` from an unrelated downstream call, in this case) may not point at the actual defect. When a request fails in a way that doesn't match any manual reproduction, check the actual server log for the *specific* request in the *specific* failing run before trusting an earlier diagnosis — a stale or differently-caused log line (here, retry-driven test-data pollution, see `KNOWN_ISSUES.md`) can look identical to the real bug.

## Phase 5

- **`claims.status` is scoped to `draft`/`validation_failed`/`validated`/`approved` only — not the full 18-state architecture lifecycle.** Building `edi_generated`/`submitted`/`ta1_received`/.../`closed` into the CHECK constraint now, with no code anywhere that could ever drive a claim past `approved`, would be speculative schema design ahead of need. **Why:** matches the same deferral already used for Phase 3's `payer_id` FK — extend the constraint (and add the driving logic) exactly when Phase 6 (EDI generation/submission/acknowledgments) or Phase 7 (adjudication/remittance) actually needs the next state, not before. **How to apply:** do not add unused lifecycle states preemptively; each new state should land in the same migration as the feature that transitions a claim into it.
- **Claim-level totals are computed, not stored.** `claims` has no `total_charge` column; the UI and validation both sum `claim_lines.charge_amount` on read. **Why:** a stored total would need to be kept in sync on every line insert/update/delete, and a sync bug (stale total after editing a line) is a worse failure mode than a cheap `reduce()` at read time for this data volume. **How to apply:** don't denormalize an aggregate onto `claims` unless a real performance need appears; recompute from `claim_lines` instead.
- **RBAC for claims is enforced with two permissive RLS policies on `claims` UPDATE — the first use of that pattern in this repo, and it has a different denial shape than Phase 4's single-policy `payers_update`.** `claims_update_edit` (`claims.create_edit`, excludes `status = 'approved'` in `WITH CHECK`) and `claims_update_approve` (`claims.approve_submit`, no such exclusion) are combined by Postgres via `OR` on `WITH CHECK` across all applicable permissive policies. **Why two policies instead of one combined expression:** the two permissions genuinely gate different things (general edits vs. the approval transition specifically), and expressing that as one policy's `WITH CHECK` would bury the RBAC boundary inside a single hard-to-read boolean rather than naming it as two independently-reasoned rules. **The denial shape is subtly different from Phase 4's `payers_update` negative, and this cost a wrong first pgTAP assertion:** Phase 4's `payers_update` policy's `USING` clause itself is `is_platform_admin()` — false for a non-admin, so the row is never selected and the `UPDATE` silently affects 0 rows, no exception. Here, `claims_update_edit`'s `USING` clause is `has_org_access` alone (true for any org member, including a `claims_specialist`), so the row *is* selected; it's `WITH CHECK` that fails across both applicable policies when a `claims_specialist` tries to set `status = 'approved'`, and Postgres throws `new row violates row-level security policy` in that case rather than silently filtering. The first draft of `claims-rls.test.sql` copied Phase 4's "assert value unchanged" pattern and got a real, unexpected `ERROR` instead of a clean pgTAP failure count. **How to apply:** when writing an RLS `UPDATE` negative test, first work out whether `USING` or `WITH CHECK` is the clause expected to fail for that specific policy shape — `USING`-failure means "assert 0 rows / value unchanged," `WITH CHECK`-failure (row was selected, but no permissive policy's check passed) means `throws_ok`. Don't assume Phase 4's pattern generalizes without checking which clause actually fails.
- **`create_professional_claim`/`create_institutional_claim` are plain `SECURITY INVOKER` functions (the default — no `security definer`), unlike Phase 2's `create_organization`/`accept_invitation`.** Those Phase 2 RPCs needed `SECURITY DEFINER` to solve a genuine bootstrap problem: a brand-new org has no members yet, so no RLS policy keyed on org membership could ever be satisfied for the very first insert. Claim creation has no such problem — the caller already has `has_org_access` and `claims.create_edit` before the RPC is ever called, so both inserts (the `claims` header and the 1:1 detail row) can run entirely under the caller's own RLS with zero privilege escalation. **How to apply:** default to `SECURITY INVOKER` for any future "atomic multi-table insert" RPC; only reach for `SECURITY DEFINER` when there's an actual bootstrap/chicken-and-egg problem like Phase 2's, and say so explicitly in the function's comment when you do.
- **Validation is wired to live `payer_rule_versions` rows, not hardcoded message strings — but the *predicates* are a fixed, known map, not a generic interpreter.** `payer_rule_versions.condition` is human-readable text (e.g. "at least one diagnosis code is present"), not a machine-executable expression — there was never a realistic MVP path to interpreting it generically. `packages/features/claims/src/lib/validate-claim.ts` instead defines one deterministic TS predicate per known seeded `rule_code`; a rule with no matching predicate is skipped, not guessed at. What *is* genuinely wired to the DB is the message: `explanation`/`suggestedCorrection`/`severity`/`rejectionOrDenial` are read fresh from the current active `payer_rule_versions` row every time validation runs, so editing a rule's text in the Phase 4 admin UI changes what a claim builder sees immediately. **How to apply:** a future phase adding a new universal/claim-type/payer-edit rule to the seed data must also add a matching predicate to `UNIVERSAL_AND_CLAIM_TYPE_CHECKS` (or the payer-edit branch) in `validate-claim.ts`, or that rule will silently never be evaluated even though it exists in the catalog.
- **The validation core is factored into a shared, non-action module (`validate-claim.server.ts`) used by both the Server Action and the REST endpoint, rather than duplicated.** `enhanceAction`-wrapped functions call `requireUser` internally and `redirect()` on failure, which doesn't fit a JSON API route handler, so the two entry points can't literally share the exported action. Instead the ~100 lines of actual validation logic (fetch claim + context, resolve applicable rules, run `evaluateClaimRules`, persist the result) live in one plain async function that both `validateClaimAction` and `POST /api/v1/claims/{id}/validate` call. **Why this matters here specifically:** Phase 4 already had a real bug caused by two code paths independently re-implementing overlapping logic and drifting apart (the CSV import schema-reuse bug above). Validation is exactly the kind of security/correctness-relevant logic where that drift risk is highest, so it gets the shared-module treatment; simpler duplications (e.g. the create-claim RPC-calling code in the action vs. the route handler) were left as direct duplication, matching Phase 4's precedent, since a two-line RPC call has much less room to drift.
- **Bug found during this phase's own Playwright verification: the institutional-claim RPC call sent an empty string, not `undefined`, for optional date fields, and Postgres rejected it.** `admissionDate`/`dischargeDate` are `z.string().optional()` in the Zod schema, and `useForm`'s `defaultValues` initializes them to `''` (not `undefined`) since they're optional inputs the user may leave blank — same general shape as the Phase 3/4 empty-string-vs-`undefined` bug class, but manifesting differently here: Zod's `.optional()` happily accepts `''` (it's not `.uuid()` or otherwise format-constrained), so validation passed silently, and the empty string reached `client.rpc('create_institutional_claim', { p_admission_date: data.admissionDate ?? undefined, ... })` — `?? undefined` only substitutes for `null`/`undefined`, not `''`, so `''` was sent as-is and Postgres's `date` parameter parser rejected it with `invalid input syntax for type date: ""`. Professional claims have no date fields, so this passed cleanly and masked the bug until the institutional flow was driven in a real browser. **Fix:** changed `?? undefined` to `|| undefined` everywhere an optional date/text field crosses the RPC boundary (both `claims.actions.ts` and the REST route), which falls through for `''` as well as `null`/`undefined`. **How to apply:** when a value that might be `''` needs to become a true SQL `NULL`/omitted-parameter, use `|| undefined`, not `?? undefined` — `??` only catches `null`/`undefined`, and Zod's `.optional()` alone does not turn `''` into `undefined`. This is now a three-occurrence variant of the same underlying class (Phase 3 provider names, Phase 4 payer rule payerId, Phase 5 claim dates) — always check what "not filled in" actually looks like in the data (`''` vs. `undefined` vs. `null`) at every boundary it crosses (client state → Zod → RPC/DB), not just the first one.

## Phase 6

- **`claims.status` is extended with only two new values (`submitted`, `accepted_for_adjudication`) — TA1/999/277CA are not separate `claims.status` values.** The architecture's state machine names TA1/999/277CA as distinct lifecycle checkpoints, but modeling each as a top-level claim status would mean a UI/API consumer has to special-case six more enum values for information that the trace (`transaction_events`/`acknowledgments`) already captures at finer, more useful grain (per-checkpoint hash, control numbers, explanation). **Why:** matches the same "don't build unused/redundant states preemptively" reasoning already applied to Phase 5's deliberately-coarse status enum. **How to apply:** when Phase 7 needs adjudication-stage claim statuses (paid/denied/etc.), only add the ones an actual UI or business rule needs to filter/branch on at the claims level — the fine-grained detail belongs in the trace, not the status enum.
- **`apps/worker` ended up owning the pure generation utilities (control numbers, synthetic X12/ack payloads, hashing) instead of `packages/features/edi`, after the original split created a real circular dependency.** The initial design put these in `@kit/edi` on the theory that `apps/worker` would import them from there (worker → edi) while `@kit/edi`'s Server Action calls into `apps/worker`'s `DeterministicClaimProcessor` (edi → worker) — that's a cycle, and `pnpm install` caught it immediately with a cyclic-workspace-dependency warning before any code had even run. **Fix:** moved `lib/control-numbers.ts`, `lib/synthetic-x12.ts`, `lib/hash.ts` into `apps/worker/src/lib/` (the only consumer that actually needs them is the processor itself), leaving `@kit/edi` with exactly one direction of dependency on `worker`. **How to apply:** when two packages need to call into each other, put the shared pure-function utilities in whichever one has no reason to depend on the other, not wherever felt more "thematically appropriate" at first glance — check `pnpm install`'s cyclic-dependency warning (or eyeball the dependency direction) before writing any code that assumes a particular import direction, not after.
- **Idempotency is guaranteed by a single `UNIQUE(claim_id)` constraint on `processing_jobs`, not a whole-pipeline database transaction.** The Supabase JS client doesn't offer a clean way to wrap ~15 sequential inserts across 7 tables in one transaction from application code the way a single RPC function could, and hand-writing that much dynamic string-building (837 payload generation, ack sequencing) in PL/pgSQL would be far more error-prone than the equivalent TypeScript. **Why this is still a real guarantee, not a compromise on the property that matters:** the specific thing being promised — "a duplicate submit produces no second processing effect" — is fully satisfied by the `processing_jobs` insert being the *first* write and using a real DB-level unique constraint: if it fails, nothing else runs, full stop, and this is provable with a plain duplicate-insert pgTAP test with no mocking. What is *not* guaranteed is that a crash between steps 2 and 6 of a single (non-duplicate) submission leaves the claim in a fully consistent state — a genuinely dropped connection mid-pipeline could leave `edi_transactions` written but `transaction_events` short a row. **How to apply:** this is an accepted MVP simplification, not a blocker — a durable-queue-based `ClaimProcessor` (the whole reason the `apps/worker` interface exists) would naturally gain retry/resume semantics later without any feature package changing. Don't try to retrofit whole-pipeline transactionality into the current synchronous path; if partial-failure recovery becomes a real requirement, it belongs in the queue-based processor, not a bigger RPC.
- **Bug found during this phase's own Playwright verification: `claims.status` (`varchar(20)` since Phase 5) was too narrow for `'accepted_for_adjudication'` (25 characters), and the failure was silent because the update's error wasn't checked.** The claim got stuck showing `submitted` in the UI while the processor's code had already gone on to insert the `accepted_for_adjudication` `transaction_events` row and mark `processing_jobs` as `completed` — i.e., the trace and the job status both claimed success while the claim itself silently never transitioned. Diagnosed by finding the actual claim left in `submitted` status in the local dev DB after the failed test run, then reproducing the exact authenticated `UPDATE` via `psql` with `set_config('request.jwt.claim.sub', ...)` to get the real Postgres error (`value too long for type character varying(20)`) — the dev server log only showed a generic PostgREST `400`, not the underlying cause, because the calling code didn't check `{ error }` and log/throw it. **Fix:** (1) widened `claims.status` to `varchar(30)` — this required first dropping both `claims_update_edit`/`claims_update_approve` RLS policies (Postgres refuses `ALTER COLUMN TYPE` on a column referenced by a policy) and recreating them after; (2) added `{ error }` checks (throwing on failure) to both claims-status `.update()` calls in `DeterministicClaimProcessor` that previously ran unchecked. **How to apply:** every `.update()`/`.insert()` call in a multi-step pipeline like this processor must check and throw on its error — an unchecked write can silently fail while later steps proceed as if it succeeded, producing exactly this kind of "the audit trail says success but the actual state disagrees" inconsistency, which is worse than a loud crash. When choosing column widths for a new enum-like text value, size for the longest string actually being stored, not a round number that happened to fit the previous phase's shorter values.
- **Bug found in the same pass: both status-badge components used `.replace('_', ' ')` instead of `.replaceAll('_', ' ')`, so multi-underscore statuses displayed wrong.** `'accepted_for_adjudication'.replace('_', ' ')` only replaces the *first* underscore (JS `String.replace` with a string pattern, not a global regex), producing "accepted for_adjudication" — silently wrong, not a crash, so it wasn't caught until the column-width bug above was fixed and the real status value could finally render. **Fix:** `.replaceAll('_', ' ')` in both `claim-detail-page-content.tsx` and `claims-list.tsx` (the `SubmitClaimButton`'s toast message already used a global regex `.replace(/_/g, ' ')` and was unaffected). **How to apply:** any future status/enum value with more than one underscore needs `.replaceAll()` or a `/g` regex for display, not `.replace()` with a string pattern — this is a general JS footgun, not specific to this codebase, worth a second look wherever a `_`-separated enum gets prettified for display.

## Phase 7

- **Adjudication outcome is a pure function of `coverage.payer_id → payer_test_profiles.default_outcome`, with the denial's triggering rule resolved via a new `payer_test_profiles.denial_rule_code → payer_rules.rule_code` join — never a per-claim-ID or per-payer-ID branch anywhere in `apps/worker`.** The Phase 4 seed data already tagged `SIM-RBH-001`/`SIM-MDMCO-001` with `default_outcome = 'denied'` as scaffolding; this phase's migration is the first thing that actually reads it, and additionally backfills `denial_rule_code` on those two rows to point at the already-seeded adjudication-category `payer_rules` (`SIM-RULE-ADJ-SIM-RBH-001`/`SIM-RULE-ADJ-SIM-MDMCO-001`). **Why this matters:** the user's kickoff instructions were explicit that the outcome must be data-driven, not hardcoded — reading the rule's live `payer_rule_versions.explanation`/`field_path` at adjudication time (not a hardcoded denial message) means editing a rule's text in the Phase 4 admin UI changes what a denied remittance explains immediately, matching the same "DB is the real content, code is the mechanism" pattern already established for claim validation in Phase 5. **How to apply:** a future payer added to the directory automatically gets `default_outcome = 'paid'` (the column's default) unless a `payer_test_profiles` row explicitly marks it denied with a `denial_rule_code` — there is no separate "list of denial payers" anywhere in application code to keep in sync.
- **CARC/RARC codes on `claim_adjustments` are always `SIM-` prefixed, resolved by a small fixed `field_path → code` map (`apps/worker/src/lib/simulated-adjustment-codes.ts`), never a real X12 CARC/RARC code.** Per `CLAUDE.md`'s non-negotiables and the user's explicit Phase 7 instruction, this repo does not have a licensed, verified source for official CARC/RARC code meanings, so asserting real codes (e.g. `197` for "precertification/authorization absent") would be fabricating claimed conformance. **Why a fixed map instead of a generic lookup:** matches the same reasoning as Phase 5's validation predicate map (`payer_rule_versions.condition` is human-readable text, not machine-executable) — there are exactly two real denial scenarios in the seed set (prior auth, benefit limit), each maps to one clearly-labeled `SIM-CARC-*`/`SIM-RARC-*` pair, and a generic fallback (`SIM-CARC-D1`) exists for any future denial rule whose `field_path` isn't in the map yet, so nothing silently crashes if a new denial payer is added before its code mapping is. **How to apply:** adding a third denial scenario means adding one entry to `DENIAL_CODES_BY_FIELD_PATH`, not inventing a new resolution mechanism; never add a real (non-`SIM-`) CARC/RARC value anywhere in this codebase without a legal/licensing review, per `CLAUDE.md`.
- **Paid claims apply a flat simulated 20% contractual write-off (`CONTRACTUAL_ALLOWANCE_RATE = 0.8` paid), not a per-payer or per-procedure fee schedule.** A real fee schedule (payer- and procedure-specific allowed amounts) is a large, separately-licensable data set with no realistic MVP substitute; a single flat simulated rate keeps the "80/20 split" demonstrably explainable (one CARC-CO adjustment row, one clear number) without pretending to model real contracted rates. **How to apply:** if a future phase wants payer-specific allowed amounts, that's a new `payer_test_profiles` column (e.g. `allowance_rate`) read the same way `default_outcome` is read now — not a hardcoded per-payer branch.
- **`remittances.claim_id UNIQUE` and `payment_matches.eft_trace_id UNIQUE` are two independent idempotency guarantees, matching Phase 6's single-unique-constraint pattern rather than inventing a new mechanism.** Adjudication and EFT-matching are two separate state transitions with two separate duplicate-prevention needs (`adjudicate()` must not double-adjudicate a claim; `matchEft()` must not double-match the same deposit), so each gets its own first-write-wins unique constraint, checked via a Postgres `23505` error code exactly the way `processing_jobs.claim_id` was in Phase 6. **How to apply:** any future new state-transition entry point in the processor should default to this same one-unique-constraint-per-transition pattern rather than trying to generalize idempotency into a shared mechanism across unrelated transitions.
- **`payment_matches` writes are gated on a new `remittances.post_payment` permission, deliberately distinct from `claims.approve_submit` (which gates `adjudicate()`).** A `claims_manager` can approve/submit/adjudicate claims but, per the seeded Phase 2 role-permission matrix, does not hold `remittances.post_payment` — only `remittance_specialist` (and `org_admin`/`org_owner`) does. **Why this split matters operationally, not just as an RBAC exercise:** adjudication is "did the payer decide to pay," a claims-side outcome; matching/posting an EFT deposit is "did the money actually arrive and get reconciled," a finance/revenue-cycle-side action in real clearinghouse operations, and the architecture's role catalog already reflects that separation of duties. **How to apply:** any future write that represents "money was received/reconciled" (as opposed to "a claim outcome was decided") should gate on `remittances.post_payment`, not `claims.approve_submit`, even if the same user happens to hold both in practice.
- **Bug found while writing this phase's pgTAP suite: `remit_claims` has two parent foreign keys (`claim_id` and `remittance_id`) but the first migration draft only installed one cross-org-consistency trigger, checking `claim_id`.** A negative test inserted a row with `organization_id` matching org1's own `claim_id` (passing that check) but `remittance_id` pointing at org2's remittance — and caught no exception, since nothing validated the `remittance_id` side at all. This is the same class of gap Phase 5/6's single-parent tables never had a chance to hit, because they only ever had one org-scoped parent FK to check. **Fix:** added a second trigger, `remit_claims_check_remittance_org`, calling a new `kit.check_remittance_child_org_consistency()` function, placed after that function's own definition in the migration file (`CREATE TRIGGER ... EXECUTE FUNCTION` resolves the function reference at creation time, so it cannot forward-reference a not-yet-defined function — trigger-function ordering in the migration file is significant). **How to apply:** any future table with more than one org-scoped parent FK needs one cross-org-consistency trigger *per parent reference*, not one trigger covering "the" parent — and the pgTAP negative for each one must actually vary only that one FK while holding the others valid, or it isn't really testing that reference.
- **PostgREST infers a `UNIQUE`-constrained child FK column as a nullable singular embed, not an array, and this changed real generated types this phase.** `remit_claims.remittance_id` and `eft_traces.remittance_id` are both `UNIQUE` (each remittance has at most one of each), so Supabase's generated types embed them from `remittances` as `RemitClaim | null` / `EftTrace | null`, not `[]` — unlike `payment_matches.remittance_id` (no unique constraint, genuinely one-to-many), which stays an array. Two component interfaces (`remittances-list.tsx`, `remittance-detail-panel.tsx`) were written assuming arrays before this was caught by `pnpm typecheck`. **How to apply:** when adding a `UNIQUE` constraint to a child table's FK column (the same pattern used for every idempotency guarantee in this codebase), always re-check the generated embed type on the parent-side select before writing component code against it — don't assume every one-to-many-shaped relationship in the schema is actually typed as an array.
- **Bug found while writing the Phase 7 Playwright suite: the coverage/enrollment dialogs retain their previously-submitted field values across re-opens (no reset-on-open), and their Payer/Status `Select` triggers have neither a `data-test` attribute nor an accessible name from `FormLabel` (the `PayerSelect` component isn't wrapped in `<FormControl>`, so no `aria-labelledby` link exists).** Every prior phase's Playwright spec only ever added one payer enrollment or one coverage per test run, so a selector matching the trigger's placeholder text (`button[role="combobox"]:has-text("Select a payer")`) always worked — the field was always genuinely empty the one time it was used. Phase 7's ten-payer acceptance sweep is the first spec to add many enrollments/coverages back-to-back on the same dialog instance in one browser session, and by the second one, the trigger's visible text was the *previous* selection's display name, not the placeholder, so the text-matching selector timed out waiting for a button that no longer said what the selector expected. **Fix:** added a `selectDialogCombobox(page, index, optionMatcher)` helper that clicks `page.getByRole('dialog').locator('button[role="combobox"]').nth(index)` — indexing by the field's fixed position in the dialog, which holds regardless of the field's current display value — and used it for both the coverage dialog's Subscriber(0)/Payer(1) fields and the enrollment dialog's Payer(0)/Status(1) fields. **How to apply:** any future Playwright helper that opens a dialog more than once per test and interacts with a `Select` whose value might already be populated from a prior submission should index by position (or add a real `data-test` attribute to the trigger, which is the more robust fix if that component is touched again) rather than matching on the trigger's current text content.
- **Bug found during this phase's own documentation review, not by any test: `remit_service_lines` — a table both the migration and the build plan explicitly call for — was fully built (schema, RLS, cross-org trigger) but `adjudicate()` never actually inserted into it.** Neither the pgTAP suite nor the Playwright suite asserted anything about this table's contents, so a completely empty table with a green test suite around it went unnoticed until writing up what Phase 7 shipped surfaced the gap between "table exists" and "table is used." **Fix:** `adjudicate()` now computes a proportional per-line payment (each `claim_lines` row gets the same `CONTRACTUAL_ALLOWANCE_RATE` applied to its own `charge_amount` for paid claims, `$0` for denied) and inserts one `remit_service_lines` row per line, and the pgTAP suite gained both an org-owned-insert assertion and a cross-org FK-consistency negative for it (bringing the suite from 16 to 18 assertions). **How to apply:** when a migration creates a table specifically because the build plan lists it, grep the processor/action code for an actual insert into that table before declaring the phase done — a table that only exists in the schema is not the same thing as a table that's part of the working feature, and neither pgTAP (which tests permissions, not application-level completeness) nor a Playwright assertion that never queries the table will catch the gap on its own.
