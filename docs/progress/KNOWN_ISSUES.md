# Known Issues / Blockers

> Anything that stops a phase's acceptance criteria from being met, recorded instead of worked around silently.

## Open

- **No UI path exists yet to grant a user the `platform_super_admin` role.** Phase 4 built the `/admin/payers` and `/admin/payer-rules` admin surfaces that role can use, and the `is_platform_admin()` RLS gate that protects them, but not a self-service or ops bootstrap flow to grant the role itself. Locally, the only way to reach those pages as an admin is a direct SQL insert (see `grantPlatformAdmin()` in `apps/e2e/tests/payers/payers.spec.ts` for the exact statement: insert a bootstrap organization, then an `organization_memberships` row with the `platform_super_admin` role for the target user). Not fixed this phase — a real bootstrap process (first-admin seeding, an ops CLI, or a `platform_super_admin`-granting invite) is out of scope for Phase 4 and should be picked up when Phase 8's governance/support-access work is scoped, or sooner if the demo needs it earlier.
- **2 pre-existing Playwright specs still fail against `next dev`, now with a clearer root cause:** `tests/account/account.spec.ts:36` ("user can update their password") and `tests/authentication/password-reset.spec.ts:11` ("will reset the password and sign in with new one") both go through a password-reset email confirmation link. When run in parallel with the rest of the suite (default Playwright config), the captured trace shows the flow lands on `/auth/callback/error?...&error=auth%3Aerrors.otp_expired` -- the confirmation link's OTP has expired by the time the test follows it, most likely because the shared local Supabase/Mailpit auth backend is rate-limited or slow to process confirmation emails under concurrent load from other specs signing up at the same time. Distinct from the dev-tools-overlay click-interception symptom resolved in Phase 2 (below). Not caused by any Phase 2 or Phase 3 change -- organizations/access-control/entities code doesn't touch the auth/password-reset path. Worth re-testing with `--workers=1` to confirm the concurrency theory; not investigated further this phase since it's outside Phase 2/3 scope -- candidate for Phase 9's full test-pyramid work.
- **Every package's `lint` script creates a stray `'node_modules'` directory (literal single-quote in the folder name)**, confirmed root cause found in Phase 2: each `package.json`'s `lint` script passes `--cache-location "'node_modules/.cache/.eslintcache'"` (extra single-quotes meant to be stripped by a POSIX shell), and in this environment (Git Bash via pnpm/turbo on Windows) those quote characters are passed through literally instead of being stripped, so ESLint creates a directory whose name literally starts with `'`. Reproduced live while staging the Phase 2 commit: running `pnpm lint` on the two new Phase 2 packages created `packages/features/{access-control,organizations}/'node_modules/.cache/.eslintcache'`, which were staged by accident and then unstaged before committing. Untracked (not matched by `.gitignore`, since the pattern is `node_modules` not `'node_modules'`), visible in `git status`, and now present under `apps/web`, every `packages/features/*` and most of `packages/*`, and `tooling/{eslint,prettier}`. Not fixed this phase (would mean editing every package's lint script + `.gitignore`, out of scope) — flagged for cleanup, and safe to delete (`git clean` won't touch them since they're not ignored, so they'd need manual removal, e.g. `rm -rf "**/'node_modules'"`).

(see below for items resolved during Phase 0 and Phase 2)

## Resolved during Phase 2

- **The floating "Open Next.js Dev Tools" button (Next.js 15 dev-mode indicator) was intercepting Playwright clicks**, documented as an open issue after Phase 1 closeout (3 failing specs: `account.spec.ts:36`, `auth.spec.ts:35`, `password-reset.spec.ts:11`). Resolved by adding `devIndicators: false` to `apps/web/next.config.mjs`. This was found while chasing a *different* bug (a Radix Dialog/DropdownMenu interaction stuck-overlay issue — see `docs/progress/DECISIONS.md`) and turned out to be an unrelated, genuine fix in its own right: `auth.spec.ts:35` ("will sign-in with the correct credentials") now passes. The other 2 specs still fail, but with a different symptom — see "Open" above.

## Resolved during Phase 0

- **pnpm not installed / not on PATH.** Node was present (`v20.8.0`) but neither `pnpm` nor `corepack enable` worked out of the box (`corepack enable` failed with `EPERM: operation not permitted, open 'E:\Node JS\pnpm.CMD'`, likely a permissions issue with the Node install location). Resolved by running `npm install -g pnpm@10.18.2`, which matches the version pinned in `package.json` (`packageManager: pnpm@10.18.2`).
- **Docker Desktop not installed.** `docker` was not on PATH and no Docker Desktop installation was found under `Program Files`. This blocks `pnpm --filter web supabase:start` and any Playwright e2e test that depends on local Supabase. User is installing Docker Desktop; local Supabase start and e2e tests will be run once it's available and the result appended to `docs/01-repository-baseline.md`.
