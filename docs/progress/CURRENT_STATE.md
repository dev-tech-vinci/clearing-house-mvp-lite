# Current State

> Snapshot of where the build stands right now. Updated at the end of every phase.

- **Last completed phase:** Phase 6 — EDI processor & trace graph (complete)
- **Branch:** `feat/bh-clearinghouse-mvp`
- **Baseline commit:** `37def9c20b01a3514cf69b5b3383bef3e5ffbcb9`
- **App state:** Multi-tenant with synthetic healthcare entities, a global payer/rules directory, a scoped claims data model, and a working synthetic EDI/trace pipeline. Phase 2 added organizations/memberships/roles/RLS. Phase 3 added providers/facilities/patients/subscribers/coverages/organization_payer_enrollments. Phase 4 added the global payer directory + versioned, explainable rules. Phase 5 added `claims`/`professional_claim_details`/`institutional_claim_details`/`claim_diagnoses`/`claim_lines`/`claim_documents`/`claim_relationships`/`claim_batches` with a draft→validate→approve workflow and RLS-enforced RBAC (`claims.create_edit` vs `claims.approve_submit`). Phase 6 adds `20260719040000_edi.sql`: `processing_jobs` (claim_id UNIQUE — the idempotency guarantee), `edi_transactions`/`edi_payloads` (synthetic 837 + control numbers, hashed), `acknowledgments` (simulated TA1/999/277CA), `rule_evaluations` (full pass/fail audit trail per submission), `replay_attempts`, and `transaction_events` (append-only — INSERT-only grant, no UPDATE/DELETE at all, proven by pgTAP). `claims.status` gains `submitted`/`accepted_for_adjudication` (column widened to varchar(30) — a real bug caught by Playwright: `varchar(20)` was too narrow for `'accepted_for_adjudication'`). New `apps/worker` app (name `worker`) hosts the `ClaimProcessor` interface + `DeterministicClaimProcessor` (no Next.js dependency, run synchronously from the submit path for the MVP). New packages `packages/features/edi` (generation utilities live in `apps/worker` to avoid a circular dependency; `edi` owns the submit Server Action + read API) and `packages/features/transaction-trace` (trace read API + UI panel, deliberately separate from `edi` since Phase 7's remittance will also write to the same `transaction_events` spine). New routes: Submit button + Transaction Trace panel on `/home/claims/[id]`. REST: `POST /api/v1/claims/{id}/submit` (honors `Idempotency-Key` header), `GET /api/v1/claims/{id}/trace`. No adjudication, denial, or 835 logic exists yet — Phase 6 never writes an adjudication-stage `transaction_events` row, enforcing the rejection-vs-denial hard rule by construction. Platform/support roles still have no cross-org RLS bypass into tenant-owned data.
- **Next phase:** Phase 7 — Adjudication simulator, remittances & reconciliation (not started; do not start until this phase's evidence is reviewed)
